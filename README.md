# Predictive Maintenance: Remaining Useful Life оценка для жёстких дисков

## Задача

Предсказать оставшийся срок службы (Remaining Useful Life, RUL) жёсткого диска в
днях на основании SMART-показателей за последний месяц эксплуатации. Регрессия,
не классификация — итоговое число дней информативнее бинарного "сломается / не
сломается", особенно с учётом бизнес-применения (планирование замены дисков).

## Данные

Источник — [Backblaze Hard Drive Test Data](https://www.backblaze.com/cloud-storage/resources/hard-drive-test-data),
квартальные датасеты с ежедневными SMART-показателями по каждому диску в
дата-центрах Backblaze.

Для проекта взят один квартал (Q1 2025), ~300 000 уникальных дисков, ~309 000
строк на файл (один файл — один день).

## Целевая переменная и censoring

RUL считается от конца первого месяца квартала (день 30) до момента поломки
диска, если она произошла в оставшиеся ~60 дней наблюдения.

Ключевая сложность: у большинства дисков поломка **не** происходит в пределах
периода наблюдения. Для них известен только факт "диск прожил ещё как минимум
60 дней", а не точный RUL. Поэтому вместо того чтобы придумывать искусственное точное значение для таких
дисков, для них используется
**нижняя граница** RUL = 60 дней, и обучение ведётся через кастомную функцию
потерь, которая не штрафует модель за переоценку censored-объектов, но
штрафует за недооценку.

### Обработка дисков, сломавшихся в первый месяц наблюдения

~377 из ~1067 сломанных за квартал дисков вышли из строя в течение самого
первого месяца — то есть до того, как накопился полный 30-дневный признаковый
период. Такие диски исключены из обучающей выборки, поскольку для них нельзя
построить X сопоставимой полноты с остальными объектами. Это ограничивает
доступный объём положительного класса до ~690 дисков.

## Признаки

Признаки строятся на основе SMART raw-показателей (`smart_*_raw`) за первый
месяц квартала, агрегированных на трёх масштабах — день, неделя, месяц — чтобы
одновременно ловить краткосрочный сигнал и общий тренд деградации.

Из рассмотрения исключены:
- `smart_*_normalized` — оставлен только raw-вариант показателей, чтобы не
  дублировать сигнал.
- Инфраструктурные идентификаторы (`datacenter`, `cluster_id`, `vault_id`,
  `pod_id`, `pod_slot_num`) — не включены как признаки, поскольку они
  специфичны для конкретной инфраструктуры Backblaze и не обобщаются на
  произвольный парк дисков. Гипотеза о корреляции отказов дисков внутри одного
  датацентра/кластера (общее питание, охлаждение, вибрация) не была
  эмпирически проверена в этой версии проекта — явное ограничение, см. ниже.
- Редкие модели дисков (менее ~500 штук в train) объединены в категорию
  `other`, чтобы не раздувать признаковое пространство почти пустыми
  one-hot-столбцами.

## Разбиение на train/val/test

70/15/15, стратифицированное по признаку поломки (`failure`), без учёта
времени. 

Явное ограничение: сплит не учитывает возможную группировку дисков по
датацентру/кластеру, что могло бы дать более консервативную (и более честную)
оценку качества, если диски внутри одной физической инфраструктуры отказывают
скоррелированно.

## Функция потерь

Стандартная MSE неприменима напрямую из-за censoring. Реализована кастомная
**censored MSE**:

- Для дисков с известным точным RUL — обычная квадратичная ошибка в обе
  стороны.
- Для censored-дисков (нижняя граница RUL = 60) — ошибка считается только если
  предсказание **ниже** границы; переоценка не штрафуется.

Функция реализована как:
- eval-метрика (для отчётности и сравнения моделей);
- custom objective (градиент + гессиан) для CatBoost (`calc_ders_range`) и
  XGBoost (через low-level и sklearn-совместимые сигнатуры отдельно, так как
  они различаются).

Дополнительно используется взвешивание объектов (`sample_weight`) для
балансировки редкого положительного класса — тот же принцип, что
`scale_pos_weight` в антифрод-проекте, но применённый через универсальный
`sample_weight`, поскольку `scale_pos_weight` специфичен для бинарной
классификации и не имеет прямого аналога в регрессии.

### Эксперимент с относительным взвешиванием (`sample_weight / target`)

Дополнительно опробовано домножение веса на `1/RUL` — попытка сместить
приоритет модели в сторону точности на дисках, близких к поломке (где ошибка
в несколько дней критичнее, чем та же ошибка на диске с большим запасом
времени). Результат подтверждён на отложенной выборке:

| | до | после |
|---|---|---|
| Средняя абс. ошибка, close-to-failure (RUL ≤ 15 дней) | 28.9 | 18.8 |
| Средняя абс. ошибка, remaining RUL > 15 дней | 12.7 | 14.1 |

Улучшение точности на критичном для бизнеса диапазоне (близкие к поломке диски)
достигнуто ценой небольшого ухудшения на дальнем горизонте — итоговое решение:
включить это взвешивание в финальную модель.

## Модели и результаты

Три семейства моделей сравнивались на одинаковом train/val:

| Модель | Val CMSE (без relative weighting) |
|---|---|
| Константный baseline | — (не считался отдельно, но линрег без сигнала близок к нему) |
| Linear Regression / Ridge / ElasticNet | ~130 (после устранения переобучения через регуляризацию и стандартизацию признаков) |
| CatBoost | ~56 |
| XGBoost | ~43 |

**Важное методологическое наблюдение**: сырое сравнение по CMSE может вводить
в заблуждение. Линейная регрессия при определённых условиях демонстрировала
обманчиво низкий CMSE (~2.2), просто предсказывая значение, близкое к 60,
почти для всех объектов — из-за структуры censored-лосса такая стратегия
почти не штрафуется на подавляющем большинстве (censored) объектов. Реальная
дискриминативность модели (отличает ли она failed от healthy дисков)
проверялась отдельно через сравнение распределений предсказаний по группам, а
не через одну агрегированную метрику.

**Финальная модель: XGBoost** (`learning_rate=0.3, max_depth=6,
min_child_weight=1, reg_lambda=10`), обученный с censored objective и
`sample_weight = class_balance_weight / RUL`.

## Известные ограничения и направления для развития

1. **Censored MSE vs полноценный survival analysis.** Текущий подход —
   практичный компромисс, но не заменяет специализированные модели
   времени-до-события (Cox proportional hazards, accelerated failure time
   models), которые изначально спроектированы для работы с censoring.
2. **Точность на близких к поломке дисках остаётся ниже, чем хотелось бы**
   (абсолютная ошибка ~18-19 дней даже после relative weighting) — вероятно,
   следствие малого числа примеров в этом диапазоне и высокой дисперсии
   индивидуальной деградации дисков.
3. **Сплит без учёта инфраструктурной группировки** (датацентр/кластер) —
   потенциальный источник оптимистичной оценки, если отказы дисков внутри
   одной физической инфраструктуры скоррелированы. Гипотеза не проверена
   эмпирически в этой версии.
4. **Один квартал данных.** Расширение периода наблюдения увеличило бы число
   доступных случаев поломки, но требует пересмотра подхода к загрузке данных
   (текущий pipeline не масштабируется на весь объём Backblaze без
   потоковой обработки).
5. **Диски, сломавшиеся в первый месяц наблюдения, исключены** (~377 из
   ~1067) — реальная потеря сигнала на самом ценном (и самом редком)
   подмножестве данных.
6. **numba-оптимизация custom objective для CatBoost не задействована**
   полностью — векторизованная реализация несовместима с автоматической
   JIT-компиляцией CatBoost; для этого пришлось переписать `calc_ders_range` в
   поэлементном стиле, менее эффективном на уровне чистого Python, но
   пригодном для JIT.
